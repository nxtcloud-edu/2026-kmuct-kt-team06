# 기술 스택 — 무엇을 풀려고 했고, 어떻게 풀었나

> 기술마다 **① 풀려던 문제 → ② 고른 기술 → ③ 어떻게 풀었나 → ④ 결과와 남은 한계** 순서로 적는다.
> 숫자는 전부 2026-09-20 당일 실측이고 재현 명령은 [`DEMO-NUMBERS.md`](DEMO-NUMBERS.md), 터진 일의 기록은 [`AS-BUILT-0920.md`](AS-BUILT-0920.md).

## 한눈에

| 층 | 기술 | 풀려던 문제 |
|---|---|---|
| 정렬 | TF-IDF + 단조 제약 동적계획법 (Python 표준 라이브러리) | 영상 없이 녹음과 PDF만으로 "이 말은 몇 번 슬라이드, 몇 초"를 정한다 |
| 음성 인식 | xAI Grok STT + 다글로, `difflib` 일치율 | 한국어 강의(영어 전문용어 섞임)를 시각과 함께 받아 적고, **틀렸을 곳을 표시**한다 |
| 출처 | 평문 앵커 토큰 `[[L1#s5@t=376]]` | 요약 문장과 원본의 그 초를 끊어지지 않게 잇는다 |
| 에이전트 | 자체 도구 루프 + 공급자 어댑터(OpenAI·Anthropic·Gemini, urllib) | 모델 이름이 죽고 API 형식이 제각각인 상황에서 컴파일을 끝까지 돌린다 |
| 통제 | 훅(서브프로세스, JSON in/out) 3곳 + 규칙 11개 | 프롬프트는 부탁일 뿐이다. 형식 위반·지어낸 출처를 **강제로** 막는다 |
| 비평 | 서로 다른 공급자 2개 + 불일치 시 8회 표본, 판정은 코드 | 모델의 자기 확신도는 보정되지 않는다 |
| 질의응답 | 조사 제거 + IDF 문단 점수, 앵커 부분집합 검증 | 위키 밖 지식으로 답하거나 출처를 지어내는 것을 막는다 |
| 저장 | 마크다운 + JSON 파일, `.history.jsonl` | 3시간 안에 DB 운영 없이, 모든 변경이 추적되게 |
| 위키 렌더 | Quartz 4 + 빌드 래퍼 | 마크다운을 그대로 읽기 좋은 사이트로 |
| 백엔드 | Python 표준 라이브러리 `http.server` | 의존성 0으로 어디에나 올린다. 오디오 탐색(Range)까지 |
| 프론트 | 바닐라 JS SPA, KaTeX 로컬 번들 | 신뢰할 수 없는 텍스트를 안전하게 그리고, 그 초로 정확히 재생한다 |
| 미디어 | ffmpeg(faststart·loudnorm), poppler | 브라우저가 27MB 녹음의 12분 40초로 바로 가게 한다 |
| 배포 | Caddy(HTTPS) + tmux + rsync | 발표장에서 빠르게, 실강의 데이터는 저장소 밖으로 |
| 개발 방식 | Kiro 4레인 + 상황판 + 커밋 차단 훅 | 네 사람의 에이전트가 같은 저장소에서 부딪히지 않게 |

## 1. 슬라이드 ↔ 음성 정렬 — TF-IDF + 단조 제약 동적계획법

**풀려던 문제.** 학생이 가진 것은 녹음 파일과 슬라이드 PDF뿐이다. 화면 녹화가 없어 장면 전환 감지를 쓸 수 없다. 그런데 제품의 핵심("그 슬라이드, 그 초")은 구간표가 있어야 성립한다.

**어떻게 풀었나.** (`tools/align_slides.py`, 모델 호출 0회)
1. 슬라이드마다 **그 슬라이드에만 나오는 단어**에 높은 가중치(TF-IDF). 다글로가 영어를 한글로 받아 적는 일이 잦아 `register→레지스터` 같은 발음 표기를 덧붙인다.
2. 전사 문단 × 슬라이드 점수표를 만든다.
3. **"슬라이드는 앞으로만 넘어간다"**는 제약 아래 점수 합이 최대인 분할을 동적계획법으로 찾는다 — 말 없이 넘어간 슬라이드는 자연히 건너뛴다.
4. "다음 슬라이드" 같은 단서 표현 쪽으로 경계를 당긴다. 구간마다 `자기 점수 ÷ (자기 + 차순위)`를 계산해 낮으면 검토함 카드로 올린다.
5. 결과는 `hooks/frame_guard.py`가 검사한다 — 길이 0·겹침·역순이면 파이프라인이 멈춘다.

**결과와 한계.** 결정론적이라 같은 입력에 같은 결과. 경계 오차 중앙값 **16초**(단서가 있는 경계 7곳: 0·3·12·16·29·32·54초). 다글로 전사가 45초 안팎 문단 단위라 ±50초가 원리적 한계다 — Grok 은 단어별 시각을 주므로 문장 단위로 바꾸면 줄일 수 있다. 당일 시스템소프트웨어 강의에서 길이 0 구간이 나와 입력 검사가 실제로 막았다.

## 2. 음성 인식과 그 불확실성 — Grok STT × 다글로, 교차 일치율

**풀려던 문제.** 멘토의 첫 질문이 이것이었다: *"STT 가 틀리면? 모델 두 개가 둘 다 높은 확신도를 주면 어떻게 판단하나?"* 모델이 스스로 매긴 0~1 은 보정되지 않는다. 틀리고도 0.98 을 준다.

**어떻게 풀었나.** 확신도를 **묻지 않는다.** 같은 녹음을 서로 다른 회사의 엔진 둘로 받아 적고, 문장마다 글자 단위 일치율을 `difflib` 으로 계산한다(`tools/stt_agree.py`). 자기 보고가 아니라 **두 엔진이 실제로 다르게 받아 적었다는 관측**이다. 0.5 미만은 🗣 인용 금지 + 검토함, 0.8 미만은 🔈 표시. 사람이 고치면(`POST /api/transcript/fix`, 훅 통과) 그 문장은 정답으로 고정된다.

**"같은 엔진을 두 번 돌리면 안 되나?" — 실험했다.** (L1 54분, 734문장)

| 비교 | 평균 일치율 | 의심 문장(<0.8) |
|---|---|---|
| Grok × 다글로 | 0.885 | **131** |
| Grok × Grok (같은 조건) | 0.990 | 8 |
| Grok × Grok (0.94배속·다른 청크) | 0.954 | 41 |

다른 엔진이 의심한 131문장 중 같은 조건 재실행이 잡은 것은 **6개**. 같은 엔진은 같은 곳에서 똑같이 틀린다("사인 익스텐션" — 다글로와 0.33, Grok 재실행과는 1.00). 검증이 되려면 **오류가 독립**이어야 한다. 속도를 바꿔 입력을 흔드는 재실행은 음향적으로 불안한 구간을 일부(22개) 드러내 보조 신호로는 쓸 수 있다.

**결과와 한계.** Grok STT 는 54분을 48초에 전사한다. 일치율은 **정확도가 아니다** — 표기 차이("Make the common case fast" vs "메이크 더 커먼 케이스 패스트")에 과민하고, 둘이 똑같이 틀리는 경우를 놓친다. 그래서 "사람이 먼저 볼 순서"로만 쓰고, 최종 방어는 모든 문장에서 원본 음성이 한 클릭이라는 것이다. 업로드 경로는 아직 STT 가 한 벌이라 일치율이 없다(두 번째 엔진 필요). 정답 전사 대비 글자 오류율은 재지 않았다.

## 3. 출처 — 평문 앵커 `[[L1#s5@t=376]]`

**풀려던 문제.** 요약과 원본 사이의 링크가 LLM 을 거치는 동안 살아남아야 하고, 마크다운 어디서든(위키·채팅 답변·필기) 같은 방식으로 동작해야 한다.

**어떻게 풀었나.** 링크를 메타데이터가 아니라 **본문 속 평문 토큰**으로 둔다. 초는 ②정렬 단계에서 코드가 확정하고, 모델은 그 토큰을 **옮겨 적기만** 한다. 새로 만들거나 고치면 쓰기 훅(R05)이 `segments.json` 과 대조해 거부한다(슬라이드 번호 일치 + 초가 그 구간 안). 프론트는 정규식으로 토큰을 찾아 칩으로 바꾸고, 누르면 `GET /api/source` 로 슬라이드·미디어·그 시각의 발언을 받는다.

**결과.** 현재 위키에 앵커 615개. 채팅 답변에서도 같은 토큰이 인라인 칩이 된다.

## 4. 에이전트 루프와 LLM 계층 — 자체 도구 루프 + 공급자 어댑터

**풀려던 문제.** 당일 실제로 겪은 것: 기본 모델 이름이 죽어 있었다(404), OpenAI 는 두 번째 턴에서 400(도구 호출 기록의 직렬화 형식), `.env` 에 키를 넣어도 읽는 코드가 없었다, 어댑터가 에이전트 이름 `"qa"` 를 모델 이름으로 넘겼다(키 없는 환경에서는 우아한 실패 처리에 가려 아무도 몰랐다).

**어떻게 풀었나.** (`pipeline/llm.py`, SDK 없이 `urllib`)
- 내부 표현을 하나로 통일(`{text, tool_calls:[{id,name,arguments}], model}`)하고 공급자별로 변환한다. 한 공급자가 429/5xx/404 면 다음으로 넘어간다.
- 역할은 `fast`/`strong` 등급으로만 부르고 모델 이름은 환경변수로 덮을 수 있다(이름은 자주 죽는다).
- 에이전트마다 도구 허용 목록을 둔다(AgentGuard). 목록 밖 호출은 실행하지 않고 그 사실을 돌려준다. 셸·파일 쓰기 도구는 아예 주지 않는다.
- 주제당 최대 20턴, 같은 페이지 쓰기 3회. 읽기만 하고 끝내려 하면 코드가 한 번 재촉한다.
- 스킬 본문은 프롬프트에 넣지 않고 **경로 목록만** 주어 필요할 때 읽게 한다(토큰 절약).

## 5. 통제 — 훅 3곳, 규칙 11개

**풀려던 문제.** 프롬프트는 부탁이고, 부탁은 어겨진다.

**어떻게 풀었나.** 에이전트는 파일시스템에 손이 없다. 쓰는 길은 `write_page` 도구 하나이고, 오케스트레이터가 그 호출을 **실행 전에** 가로채 `hooks/write_page_guard.py` 를 서브프로세스로 띄운다. stdin 으로 `{agent, tool_name, tool_input:{path, content}}`, stdout 으로 `allow` 또는 `block + REJECTED: 사유 + 규칙 ID`. Claude Agent SDK·Kiro 의 PreToolUse 훅과 같은 규격이라 개발 도구(Kiro 의 커밋 차단)와 제품이 같은 방식을 쓴다.

| 훅 | 시점 | 막는 것 |
|---|---|---|
| 입력 `frame_guard` | 적재 직후 | 길이 0·겹침·역순 구간 |
| 쓰기 `write_page_guard` | 모든 파일 쓰기 직전(에이전트·사람) | 허용 폴더 밖·경로 탈출·HTML 삽입·앵커 없는 📄/🗣·**구간표에 없는 앵커**·콜아웃 밖 외부 링크·깨지는 프론트매터·사용자의 본문 수정 |
| 출력 `qa_stop_guard` + 코드 | 채팅 답변 직후 | 앵커 없는 답 · **제공한 근거에 없는 앵커를 인용한 답** |

거부 사유는 원문 그대로 모델에게 돌아가고, 모델은 사유에 적힌 곳만 고쳐 다시 쓴다. 모든 시도는 `wiki/.history.jsonl` 에 남아 대시보드의 반려 로그가 된다. 사람의 필기·승인·숨기기·제목 수정도 같은 훅을 `agent: user` 로 통과한다(상태·제목 줄만, 본문은 바이트 동일).

**결과.** 첫 4편 컴파일에서 쓰기 53회 중 거부 7회, **7회 모두 재작성으로 통과**, 끝내 막힘 0.

**규칙은 실패에서 자란다 — 당일 세 번.**
1. 에이전트가 제목에 `: ` 를 넣어 YAML 이 깨지고 **사이트 빌드 전체가 죽었다** → 제목 규칙 추가 + 빌드용 복사본에서 프론트매터 보정(원본 불변).
2. 노트가 길어지자 에이전트가 새 주제만 보내 훅이 "프론트매터 없음"으로 계속 거부, 7주제 중 5개가 버려졌다 → 훅은 옳았고 설계가 틀렸다. **노트 조립을 코드로 옮겼다**(에이전트는 주제 섹션만 보낸다).
3. 채팅이 위키에 없는 출처를 지어냈다 → 출력 쪽에 앵커 부분집합 검증 추가.

**한계.** 훅은 형식과 존재만 본다. 그 구간에 그 내용이 정말 있는지는 비평 단계와 사람의 몫이다.

## 6. 비평 — 두 공급자, 범주형 질문, 판정은 코드

**풀려던 문제.** "이 요약이 맞나"를 모델에게 물으면 대체로 "맞다"고 한다. 확신도 숫자는 보정되지 않는다.

**어떻게 풀었나.** (`pipeline/critic.py`) 🗣 인용은 코드가 그 구간 전사본과 문자 유사도로 대조한다. 문단은 **그 앵커 구간의 전사본만** 보여 주고 JSON 한 줄(`supported: yes|no|partial`, `quote_faithful`, `from_untrusted`, `evidence`)로 답하게 한다. 같은 질문을 **서로 다른 공급자 2개**에 묻고, 갈리면 8회 반복해 답의 분포를 본다. `no` 가 있으면 재작성, `partial` 이면 검토함, 전부 `yes` 면 통과 — 이 판정은 코드다.

**결과와 한계.** 인용 대조 23/23. 비평 자체의 정확도는 정답 라벨이 없어 재지 못했다. 당일에는 비평이 의심 페이지를 자동으로 숨김 처리해 13쪽 중 8쪽이 화면에서 사라지는 일이 있었고, "비평은 판정만, 숨기기는 사람만"으로 고쳤다.

## 7. 질의응답 — 근거 선택과 출처 검증

**풀려던 문제.** 처음 구현은 페이지 순서대로 앞의 8문단을 근거로 주었고, "머지소트의"처럼 조사가 붙은 단어는 검색에 걸리지도 않았다. 모델은 아는 지식으로 답하고 출처를 지어냈다.

**어떻게 풀었나.** (`api/qa.py`) 조사를 떼고("머지소트의"→"머지소트") 띄어쓰기를 무시하며, 드문 단어에 가중치(IDF)를 준 **문단 단위 점수**로 상위 10개를 고른다. 근거가 0개면 모델을 부르지 않는다(0.0초). 답의 앵커가 근거 문단의 앵커 집합에 속하는지 코드가 비교해, 아니면 어느 앵커가 틀렸는지 알려 1회 재생성하고 그래도 아니면 폐기한다. 숨긴 페이지는 근거에서 뺀다.

**결과.** 벡터 DB·임베딩 없이 3~5초. 수정 후 실측 질문에서 근거 밖 앵커 0. 평가 질문 세트는 아직 없다.

## 8. 저장과 렌더 — 파일이 곧 데이터, Quartz

**풀려던 문제.** 3시간에 DB 를 세우고 운영할 수 없고, "누가 무엇을 언제 바꿨나"가 남아야 한다. 실강의 자료는 저장소에 올라가면 안 된다.

**어떻게 풀었나.** 위키는 YAML 프론트매터가 붙은 마크다운, 구간표·전사본은 JSON, 감사 기록은 한 줄 JSON(`.history.jsonl`). 실강의 산출물은 전부 `.gitignore`. 그런데 Quartz 는 `.gitignore` 를 따라 그 파일들을 빌드에서 빼 버린다 → `tools/build_wiki.py` 가 위키를 임시 폴더로 복사해 거기서 빌드한다(숨긴 페이지 제외, 프론트매터 보정, 변경 폴링 3초). 같은 시점에 뷰어용 목록과 노트별 예상 질문 캐시도 다시 만든다.

## 9. 백엔드 — Python 표준 라이브러리만

**풀려던 문제.** 발표장 서버에 무엇이 깔려 있을지 모른다. 실제로 당일 서버를 EC2 → OCI 로 옮겼고 Python 은 3.10 이었다.

**어떻게 풀었나.** `http.server.ThreadingHTTPServer` 하나가 정적 파일과 API 18경로를 **같은 오리진**에서 준다(CORS 없음). 직접 구현한 것: 오디오 탐색을 위한 Range(206) 응답, `/web/../.env` 같은 경로 탈출 차단, multipart 업로드, 오류 봉투 `{error:{code,message}}`, 쓰기·과금 경로의 토큰 보호, IP당 분당 10회 제한. `pip install` 이 없다.

## 10. 프론트 — 바닐라 JS, 안전한 렌더, 정확한 재생

**풀려던 문제와 해결.**
- **신뢰할 수 없는 텍스트**(전사·필기·모델 출력)를 그린다 → `innerHTML` 0건, 전부 `textContent`. 채팅 답변의 마크다운·수식은 자체 파서(`web/notes/richtext.js`)가 DOM 노드로 만든다. KaTeX 는 `trust:false`, 수식 길이 상한.
- **발표장에서 CDN 이 안 될 수 있다** → KaTeX 를 저장소에 번들(596KB).
- **칩을 눌러도 0초부터 재생됐다** → 녹음의 색인이 파일 끝에 있었고 seek 을 한 번만 했다. 파일은 faststart 로, 재생은 `#t=` + `loadedmetadata` + `canplay` 세 번 확인.
- **새 브라우저에서 채팅이 가짜 답을 냈다** → 샘플 모드 기본값이 켜져 있었다. 기본을 실서버로.
- **화면에 견본만 보였다** → 뷰어가 커밋된 고정 목록만 읽었다. 위키에서 목록을 생성하는 도구를 빌드에 연결.
- 업로드는 단계 표시·진행률(뒤로 가지 않게 단조)·새로고침 후 재개, 과목은 선택 + 추가.

## 11. 미디어·문서 처리 — ffmpeg, poppler

`pdftoppm`(슬라이드 PNG) · `pdftotext`(쪽별 텍스트 → 정렬의 입력). `ffmpeg -movflags +faststart`(색인을 앞으로) · `loudnorm`(−39dB 로 녹음된 강의를 −17dB 로) · `atempo`(교란 재실행 실험).

## 12. 배포 — Caddy + tmux + rsync

**풀려던 문제.** EC2(us-east-1)는 응답이 0.42초였다. 조직 저장소라 서버에 git 인증을 두기 어렵고, 실강의 데이터는 애초에 저장소에 없다.

**어떻게 풀었나.** 가까운 리전 서버(도쿄)로 옮기고(0.22초) Caddy 로 HTTPS 와 업로드 한도(520MB)를 준다. 코드는 rsync, 데이터·키는 따로 rsync. 서비스는 tmux 두 세션(위키 빌드 감시 · API, 죽으면 2초 뒤 재시작). 절차는 [`DEPLOY.md`](DEPLOY.md).

## 13. 개발 방식 — Kiro 4레인과 상황판

**풀려던 문제.** 네 사람이 각자 노트북에서 Kiro 를 돌리면 서로 무엇을 하는지 모르고, 에이전트가 제멋대로 커밋·푸시한다.

**어떻게 풀었나.** 레인 = 한 에이전트가 소유한 디렉터리. 레인마다 Kiro spec(requirements·design·tasks)과 steering. **PreToolUse 훅으로 에이전트의 `git commit`·`push` 를 차단**하고 커밋 제안만 하게 했다. 진행은 [상황판](https://github.com/PROVE1352/kirothon-board)(토큰 + IP 허용 목록의 작은 HTTP 보드)으로 모으고, 레인 밖 결정은 `human` 요청으로 올라와 디스코드에서 팀장이 승인한다 — 올라오면 다른 모델 둘이 의견과 반론을 단다. 제품의 원칙(코드가 통제하고, 사람은 기계가 못 거른 것만 본다)을 개발 과정에도 그대로 썼다.
